# Сервер для Shado: что нужно сделать

> **Исторический документ.** Это исходный план, по которому сделан сервер; он
> описывает уроки как личные записи пользователя (`lessons.user_id`, «`audio_id`
> принадлежит тому же пользователю»). С тех пор модель доступа изменилась: уроки
> стали общим каталогом, который ведут роли `admin` и `owner`, а колонка
> называется `author_id`. Актуальные правила — в [README](../README.md) и
> [CLIENT_SPEC](CLIENT_SPEC.md), схема — в `migrations/`.

Приложение сейчас работает полностью локально. Задача — перенести уроки (текст,
разбивку, аудио) на сервер и добавить авторизацию, не переписывая домен и UI.

Швы под это заложены с самого начала (см. `SHADOWING_MVP_PROMPT.md`, раздел 9):
идентификаторы — клиентские UUID, модели уже JSON-сериализуемы,
`LessonRepositoryImpl` — единственное место, куда добавляется удалённый источник.

---

## 1. Открытая развилка: стек

Единственное решение, которое надо принять до начала работ.

| Вариант | Что даёт | Чего стоит |
| --- | --- | --- |
| **Свой API** (рекомендую: Dart + `dart_frog`/`shelf` + Postgres + S3-совместимое хранилище) | Полный контроль, общий язык с приложением, можно переиспользовать `freezed`-модели как DTO сервера | Аутентификацию, хранилище файлов, миграции и деплой пишем сами |
| **BaaS** (Supabase: Postgres + Auth + Storage + RLS) | Регистрация, токены, refresh, загрузка файлов и права доступа — из коробки, за день | Транскодирование и предподсчёт пиков всё равно свои (Edge Function); привязка к платформе |

Рекомендация: если цель — быстро получить работающую синхронизацию, брать
**Supabase** и вынести обработку аудио в одну функцию. Если сервер планируется
развивать (шаринг уроков, генерация, платежи) — **свой API на Dart**.

Всё, что ниже, от выбора не зависит: контракт, схема данных и порядок работ
одинаковы. Дальше «сервер» — любая из двух реализаций.

## 2. Модель данных на сервере

Postgres. Сегменты — как и локально, частью агрегата урока (`jsonb`): они всегда
читаются и пишутся вместе с уроком, отдельные запросы по ним не нужны.

```sql
create table users (
  id            uuid primary key,
  email         text not null unique,
  password_hash text not null,           -- argon2id
  created_at    timestamptz not null default now()
);

create table refresh_tokens (
  id          uuid primary key,
  user_id     uuid not null references users on delete cascade,
  token_hash  text not null unique,      -- храним хеш, не сам токен
  family_id   uuid not null,             -- цепочка ротации, для detection reuse
  expires_at  timestamptz not null,
  revoked_at  timestamptz,
  user_agent  text
);

-- Аудио живёт отдельно от урока: файл загружается ДО создания урока (см. §5).
create table audio_files (
  id            uuid primary key,
  user_id       uuid not null references users on delete cascade,
  storage_key   text not null,           -- ключ в S3 / Storage
  content_type  text not null,
  size_bytes    bigint not null,
  sha256        text not null,
  duration_ms   integer not null,        -- посчитан сервером
  peaks         bytea not null,          -- огибающая, int8, высокое разрешение
  peaks_count   integer not null,
  created_at    timestamptz not null default now(),
  unique (user_id, sha256)               -- повторная загрузка того же файла бесплатна
);

create table lessons (
  id          uuid primary key,          -- UUID приходит с клиента
  user_id     uuid not null references users on delete cascade,
  audio_id    uuid not null references audio_files,
  title       text not null,
  duration_ms integer not null,
  segments    jsonb not null,            -- [{index, text, start_ms, end_ms}]
  created_at  timestamptz not null,      -- приходит с клиента
  updated_at  timestamptz not null default now(),
  deleted_at  timestamptz,               -- мягкое удаление: чтобы разошлось по устройствам
  version     integer not null default 1 -- для If-Match
);

create index on lessons (user_id, updated_at desc);
```

Инварианты, которые сервер обязан проверять (они же проверяются в домене
приложения, но серверу нельзя верить клиенту):

- сегментов ≥ 1, `index` идут `0..N-1` без дыр;
- границы строго возрастают, `segments[0].start_ms = 0`,
  `segments[N-1].end_ms = duration_ms`;
- `duration_ms` урока равен `duration_ms` его аудио;
- `audio_id` принадлежит тому же пользователю.

## 3. Аутентификация

Email + пароль, JWT: короткий access-токен и долгий refresh с ротацией.

| Метод | Путь | Тело / ответ |
| --- | --- | --- |
| POST | `/v1/auth/register` | `{email, password}` → `{user, access_token, refresh_token, expires_in}` |
| POST | `/v1/auth/login` | то же |
| POST | `/v1/auth/refresh` | `{refresh_token}` → новая пара (старый refresh гасим) |
| POST | `/v1/auth/logout` | `{refresh_token}` → 204 |
| GET | `/v1/me` | → `{id, email, created_at}` |

Требования:

- пароли — argon2id (или bcrypt cost ≥ 12), минимум 8 символов;
- access-токен 15 минут, refresh 60 дней, **ротация при каждом обновлении**; если
  пришёл уже погашенный refresh — гасим всю цепочку `family_id` (признак кражи);
- rate limit на `/auth/*`: например 10 попыток в минуту на IP и на email;
- одинаковый ответ на «нет такого email» и «неверный пароль» — не подсказываем,
  какие адреса зарегистрированы;
- ошибки одним форматом на весь API: `{"error": {"code": "invalid_credentials",
  "message": "..."}}`, HTTP-код по смыслу.

На клиенте: refresh-токен только в `flutter_secure_storage` (не в
`SharedPreferences`), access — в памяти. Интерсептор на 401: один параллельный
запрос на refresh, остальные ждут его и повторяются.

## 4. API уроков

Форма JSON намеренно совпадает с текущими `LessonModel` / `SegmentModel`
(`snake_case`, времена — ISO-8601 UTC, всё в миллисекундах), плюс серверные поля.

```json
{
  "id": "9f1c…",
  "title": "TED: How to learn",
  "duration_ms": 183400,
  "created_at": "2026-07-28T10:00:00.000Z",
  "updated_at": "2026-07-28T10:12:03.000Z",
  "version": 3,
  "audio": {
    "id": "b21e…",
    "url": "https://api.shado.app/v1/audio/b21e…/file",
    "content_type": "audio/mpeg",
    "size_bytes": 2938471,
    "sha256": "3f2a…",
    "duration_ms": 183400
  },
  "segments": [
    { "index": 0, "text": "Hello there.", "start_ms": 0, "end_ms": 2100 },
    { "index": 1, "text": "How are you?", "start_ms": 2100, "end_ms": 4300 }
  ]
}
```

| Метод | Путь | Смысл |
| --- | --- | --- |
| GET | `/v1/lessons?since=<iso>&limit=&cursor=` | список, `updated_at desc`; с `since` — дельта, включая удалённые (`deleted_at`) |
| GET | `/v1/lessons/{id}` | один урок, отдаёт `ETag: "<version>"` |
| PUT | `/v1/lessons/{id}` | создать **или** обновить: `{title, audio_id, created_at, segments}`; при обновлении `If-Match: "<version>"` |
| DELETE | `/v1/lessons/{id}` | мягкое удаление, 204 |

Почему `PUT`, а не `POST`: UUID урока генерирует клиент (`_uuid.v4()` в
`LessonRepositoryImpl`), поэтому создание идемпотентно — повтор после потери сети
не создаёт дубль. Тот же метод обслуживает и правку урока: сегменты приходят
целиком, потому что это агрегат (ровно так же работает
`LessonLocalDataSource.upsertLesson` и use case `UpdateLessonContent`).

Конфликт версий → `409` с текущим состоянием урока в теле. Для приложения на
одного пользователя это редкость (два устройства правят один урок), но правило
дешёвое, а без него правки молча теряются.

## 5. Аудио: загрузка, пики, выдача

Здесь у сервера самая большая польза, и порядок шагов важен — он должен совпасть
с тем, как уже устроен экран создания урока.

### Загрузка идёт ДО создания урока

Экран «Добавить» сейчас работает так: выбрали файл → узнали длительность →
нарисовали волну с метками → и только потом «Создать урок». Значит сервер должен
уметь принять файл сам по себе и сразу вернуть всё, что нужно для отрисовки:

```http
POST /v1/audio            multipart: file
→ 201 { id, content_type, size_bytes, sha256, duration_ms,
        url, peaks: { resolution: 2000, minima: "<base64 int8>", maxima: "…" } }
```

Если файл с таким `sha256` у пользователя уже есть — `200` и та же запись, без
повторной загрузки и обработки.

Что сервер делает при загрузке:

1. проверяет тип (`mp3, m4a, wav, flac, ogg`) и размер (например ≤ 50 МБ);
2. считает `duration_ms` — **это снимает с клиента локальный замер**
   (`AudioFileDataSource.resolveDurationMs` через `just_audio`/libmpv);
3. строит огибающую (ffmpeg/ffprobe) в высоком разрешении и складывает в
   `audio_files.peaks`;
4. по желанию нормализует формат: перекодирует в mp3 44.1 кГц. **Это лечит
   существующее ограничение**: на Windows/Linux декодер `flutter_soloud` не читает
   m4a/aac, поэтому загруженный с iPhone урок сейчас остаётся без волны.

### Пики отдаёт сервер

```http
GET /v1/audio/{id}/peaks?resolution=2000
→ { resolution, minima: "<base64>", maxima: "<base64>" }
```

`int8` в base64: 2000 точек — это 4 КБ вместо ~30 КБ JSON-числами. Значения
нормализованы так же, как сейчас на клиенте (`maxima` 0..1, `minima` -1..0,
пик прижат к единице).

Это выгодно втройне: открытие урока перестаёт ждать секунды на декодирование,
на десктопе больше не нужен `flutter_soloud`, и волна выглядит **одинаково на
всех платформах** — сегодня mobile рисует настоящие min/max, а десктоп
RMS-огибающую.

В приложении это ровно одна новая реализация существующего интерфейса
`WaveformDataSource` (`RemoteWaveformDataSource`), локальные остаются как
запасной путь для офлайна.

### Отдача файла для воспроизведения

```http
GET /v1/audio/{id}/file      Authorization: Bearer <access>
→ 200, Accept-Ranges: bytes, ETag, Cache-Control: private, immutable
```

Обязательно поддержать `Range` — без него нельзя докачать обрыв.

**Играть по сети напрямую не нужно.** В shadowing куски зацикливаются по 2–3
секунды, и `ClippingAudioSource` поверх сетевого источника будет дёргаться на
каждом повторе. Правильный путь: при первом открытии урока файл скачивается один
раз в кеш приложения (там же, где сейчас лежит аудио), а плеер как и сегодня
работает с `AudioSource.file`. Целостность — по `sha256` из ответа.

Если хранилище S3-совместимое, вместо проксирования выдавайте presigned-ссылку на
10–15 минут: `GET /v1/audio/{id}/url → {url, expires_at}`.

## 6. Что меняется в приложении

Домен и presentation не меняются вообще — при одном условии: **репозиторий
продолжает отдавать `Lesson.audioPath` как локальный путь к готовому к
воспроизведению файлу**, только теперь этот файл он при необходимости
докачивает. Тогда плеер, волна и все экраны остаются как есть.

| Слой | Что добавляется |
| --- | --- |
| `data/datasources` | `LessonRemoteDataSource` (уроки), `AudioRemoteDataSource` (загрузка/скачивание), `RemoteWaveformDataSource` (пики) |
| `data/models` | отдельные DTO под API (`LessonDto`, `AudioDto`). `LessonModel` оставить для sqflite: локально хранится путь к кешу, на сервере — `audio_id`, и смешивать их в одной модели не стоит |
| `data/repositories` | `LessonRepositoryImpl`: сервер — источник истины, sqflite — кеш; докачивание аудио в `getLesson` |
| `features/auth` (новая фича) | `domain`: `AuthRepository`, use case'ы `login`/`register`/`logout`/`currentUser`; `data`: клиент API + `flutter_secure_storage`; `presentation`: экран входа и регистрации |
| `core/network` | http-клиент (`dio`), интерсепторы: `Authorization`, refresh на 401, повтор при сетевых сбоях |
| `core/router` | `redirect` по состоянию авторизации: без токена — на `/login` |
| Зависимости | `dio`, `flutter_secure_storage`; локальный замер длительности и `flutter_soloud` можно убрать позже, когда сервер станет обязательным |

Порядок создания урока на клиенте после переезда:

1. выбрали файл → `POST /v1/audio` (с прогрессом) → получили `duration_ms` и пики;
2. рисуем волну и расставляем метки — как сейчас, только данные не свои;
3. «Создать урок» → `PUT /v1/lessons/{uuid}` с `audio_id` и сегментами;
4. записали урок в локальный кеш, аудио уже лежит в кеше после шага 1.

## 7. Синхронизация: что делать сразу, а что потом

Сейчас достаточно простой схемы, и её стоит явно зафиксировать, чтобы не
скатиться в полноценный offline-first раньше времени:

- **сервер — источник истины**, локальная sqflite становится кешем для чтения;
- на старте и по pull-to-refresh — `GET /v1/lessons?since=<последний updated_at>`,
  применяем дельту, удалённые (`deleted_at`) выкидываем;
- запись (создание, правка, удаление) идёт на сервер, при успехе — в кеш; нет
  сети — честная ошибка в UI, как сейчас при сбое БД;
- аудио кешируется по `audio_id`, чистка кеша — по LRU и по удалённым урокам.

Полноценная офлайн-очередь (`pending_operations`, разрешение конфликтов,
дозагрузка) — отдельный этап, и он нужен только если правка уроков без сети
действительно требуется. Швы для него: `version`/`If-Match` и мягкое удаление уже
в контракте.

## 8. Нефункциональные требования

- только HTTPS, HSTS; никакого доступа к файлам без токена или presigned-ссылки;
- лимиты: размер запроса, размер файла, квота на пользователя (например 2 ГБ),
  rate limit на API;
- `deleted_at` чистится фоновым джобом через N дней вместе с осиротевшим аудио
  (аккуратно: файл может быть общим для нескольких уроков по `sha256`);
- миграции схемы под контролем (не `create table if not exists` руками);
- `GET /healthz`, структурные логи с request-id, метрики по времени обработки
  загрузок;
- бэкапы Postgres и хранилища; проверка восстановления;
- удаление аккаунта: удалить всё, включая файлы (это ещё и требование сторов).

## 9. Порядок работ

Каждый этап оставляет приложение в рабочем состоянии.

1. **Инфраструктура.** Выбрать стек (§1), домен, TLS, Postgres, хранилище,
   миграции, `/healthz`, деплой.
2. **Авторизация.** Эндпоинты `/v1/auth/*` и `/v1/me`; на клиенте — фича `auth`,
   безопасное хранение токенов, интерсепторы, экран входа, `redirect` в роутере.
   Уроки на этом шаге ещё локальные.
3. **Аудио.** `POST /v1/audio` с длительностью и пиками, выдача файла с `Range`.
   На клиенте — `RemoteWaveformDataSource` и загрузка на экране создания. Здесь же
   выравнивается поведение волны на всех платформах.
4. **Уроки.** `GET/PUT/DELETE /v1/lessons`, `LessonRemoteDataSource`, сборка
   репозитория «сервер + кеш», докачивание аудио при открытии урока.
5. **Дельта-синхронизация** по `since` и чистка кеша.
6. **Потом, по необходимости:** офлайн-очередь записи, шаринг уроков, вход через
   Apple/Google (обязателен для iOS, если появится вход через соцсети).

Тестирование: держать `LessonRemoteDataSource` и `AuthRepository` за
интерфейсами, как сейчас локальные источники, — тогда репозиторий и контроллеры
тестируются на подделках без сети. Для сервера — контрактные тесты на каждый
эндпоинт и проверка инвариантов из §2.

---

## 10. Что специально НЕ делаем

- не переносим на сервер распознавание речи и авторазметку — принцип приложения
  не меняется, разметка ручная;
- не играем аудио потоком с сервера (см. §5);
- не заводим отдельную таблицу сегментов и эндпоинты на каждый сегмент: это
  агрегат урока;
- не делаем офлайн-запись в первой версии.
