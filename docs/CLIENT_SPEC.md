# Клиент Shado: что делать и как

Спецификация под уже реализованный сервер (см. [README](../README.md)). Домен и
presentation приложения не меняются — при одном условии: **репозиторий продолжает
отдавать `Lesson.audioPath` как локальный путь к готовому к воспроизведению
файлу**, только теперь этот файл он при необходимости докачивает. Тогда плеер,
волна и все экраны остаются как есть.

Порядок работ — в конце документа (§11), там же чек-лист приёмки.

---

## 1. Общие правила API

- База: `http://127.0.0.1:8080` локально, `https://…` в проде. Все пути ниже —
  от корня, версия в пути: `/v1/...`.
- Тело запросов и ответов — JSON, `snake_case`, кодировка UTF-8.
- Времена — ISO-8601 UTC с миллисекундами: `2026-07-28T10:00:00.000Z`.
  В Dart: `DateTime.parse(...)` и `dt.toUtc().toIso8601String()`.
- Все длительности и позиции — миллисекунды, целые.
- Авторизация: `Authorization: Bearer <access_token>` на всех путях, кроме
  `/healthz` и `/v1/auth/*`.
- Идентификаторы — UUID v4 строкой. **UUID урока генерирует клиент** (как сейчас
  в `LessonRepositoryImpl`), UUID аудио — сервер.

### Формат ошибок

Один на весь API:

```json
{ "error": { "code": "validation_error", "message": "первый сегмент должен начинаться с 0" } }
```

| code | HTTP | Когда | Что делает клиент |
| --- | --- | --- | --- |
| `validation_error` | 422 | тело не прошло проверку (сегменты, email, пароль) | показать `message`, не повторять запрос |
| `invalid_credentials` | 401 | неверная пара email/пароль | «неверный email или пароль» |
| `email_taken` | 409 | email уже зарегистрирован | предложить войти |
| `unauthorized` | 401 | нет токена, токен истёк или refresh недействителен | см. §3, обновление токена или выход |
| `forbidden` | 403 | не хватает роли: правка каталога или вкладка owner | скрыть действие, не повторять |
| `not_found` | 404 | нет ресурса, он удалён **или ещё не опубликован** | обработать как «удалён на сервере» |
| `version_conflict` | 409 | правка поверх устаревшей версии | см. §6, в `error.current` лежит актуальный урок |
| `payload_too_large` | 413 | файл больше лимита (50 МБ) | сообщить размер лимита до загрузки |
| `unsupported_media_type` | 415 | формат не поддержан или файл не читается | список форматов в сообщении |
| `rate_limited` | 429 | больше 10 попыток в минуту на `/v1/auth/*` | подождать минуту, показать таймер |
| `internal_error` | 500 | сбой сервера | «попробуйте позже», залогировать |

Правило на будущее: **неизвестный `code` — это не «всё хорошо»**. Мапить по
списку, всё остальное — общая ошибка по HTTP-статусу.

### Каталог и приватность

**Публичный каталог.** Публичные уроки ведут `admin` и `owner`, а видят все
авторизованные пользователи: список публичных одинаковый для всех. Аудио
публичного урока доступно всем на чтение.

**Приватные уроки.** `user-pro` заводит собственные приватные уроки (всегда
приватные), owner может создавать приватные наравне с публичными. Приватный урок
и его аудио видит только автор: в чужом списке его нет, а по прямой ссылке — `404`,
как несуществующий. Видимость несёт поле `is_public` в теле урока (§6).

Приватна и незавершённая работа редактора: свежая загрузка `POST /v1/audio`
видна лишь тому, кто её сделал, пока на неё не сослался живой урок. Недоступный
ресурс отдаёт `404` (нет, ещё не опубликован или чужой приватный), а попытка
изменить каталог без роли — `403`. На `404` запись убирается из локального кеша,
на `403` — прячется кнопка, повторять запрос бессмысленно.

## 2. Что добавляется в приложении

| Слой | Что добавляется |
| --- | --- |
| `core/network` | `ApiClient` на `dio`: базовый URL, интерсепторы `Authorization`, refresh на 401, повтор при сетевых сбоях, единый разбор ошибок в `ApiException` |
| `core/storage` | `TokenStorage` поверх `flutter_secure_storage` (refresh-токен) + access в памяти |
| `features/auth` (новая) | `domain`: `AuthRepository`, use case'ы `login`/`register`/`logout`/`currentUser`; `data`: клиент API + хранилище токенов; `presentation`: экраны входа и регистрации |
| `data/datasources` | `LessonRemoteDataSource`, `AudioRemoteDataSource` (загрузка/скачивание), `RemoteWaveformDataSource` (пики), `TtsRemoteDataSource` (озвучка текста, см. ниже) |
| `data/models` | отдельные DTO под API (`LessonDto`, `AudioDto`, `SegmentDto`). `LessonModel` оставить для sqflite: локально хранится путь к кешу, на сервере — `audio_id`, смешивать их в одной модели не стоит |
| `data/repositories` | `LessonRepositoryImpl`: сервер — источник истины, sqflite — кеш; докачивание аудио в `getLesson` |
| `core/router` | `redirect` по состоянию авторизации: без токена — на `/login`; нижняя навигация собирается по роли (§4), маршруты создания урока и вкладка «Пользователи» — под guard |
| Зависимости | `dio`, `flutter_secure_storage`, `crypto` (проверка sha256), `path_provider` (уже есть) |

Держать `LessonRemoteDataSource` и `AuthRepository` за интерфейсами, как сейчас
локальные источники, — тогда репозиторий и контроллеры тестируются на подделках
без сети.

**Озвучка через ИИ (Gemini TTS).** Кнопка «Озвучить через ИИ» на экране
создания урока: текст уходит на `POST /v1/tts/synthesize`, ответ обрабатывается
как загрузка аудио (кеш по `audio_id`, волна по `peaks`, файл через
`GET /v1/audio/{id}/file`). Доступна **только owner** — остальным авторам
(`user-pro`, `admin`) сервер отвечает `403`, поэтому кнопку и остаток лимита им
не показываем. Полное описание — [`TTS_CLIENT_SPEC.md`](./TTS_CLIENT_SPEC.md).

## 3. Токены и сетевой слой

**Хранение.** Refresh — только в `flutter_secure_storage`, access — в памяти
(переживать перезапуск ему незачем, живёт 15 минут).

**Жизненный цикл.**

1. `register`/`login` → сохранить `refresh_token` в secure storage, `access_token`
   держать в поле `ApiClient`.
2. Старт приложения: refresh есть → сразу `POST /v1/auth/refresh`, получить
   access и данные пользователя; refresh нет или ответ 401 → экран входа.
3. Любой ответ 401 с `code: unauthorized` на обычном запросе → один параллельный
   запрос на refresh, остальные ждут его и повторяются.
4. 401 на самом refresh → полный выход: чистим secure storage, локальный кеш
   уроков и аудио, уводим на `/login`.

Пункт 4 обязателен: сервер гасит **всю цепочку** refresh-токенов, если пришёл уже
использованный (признак кражи). Тихо ретраить бессмысленно.

```dart
class AuthInterceptor extends Interceptor {
  AuthInterceptor(this._dio, this._tokens);

  final Dio _dio;
  final TokenStorage _tokens;
  Future<String?>? _refreshing; // один refresh на все параллельные запросы

  @override
  void onRequest(RequestOptions options, RequestInterceptorHandler handler) {
    final access = _tokens.access;
    if (access != null && options.extra['skipAuth'] != true) {
      options.headers['Authorization'] = 'Bearer $access';
    }
    handler.next(options);
  }

  @override
  Future<void> onError(DioException err, ErrorInterceptorHandler handler) async {
    final isAuthCall = err.requestOptions.path.startsWith('/v1/auth/');
    if (err.response?.statusCode != 401 || isAuthCall) return handler.next(err);

    final access = await (_refreshing ??= _refresh().whenComplete(() => _refreshing = null));
    if (access == null) return handler.next(err); // выход инициирует AuthRepository

    final options = err.requestOptions..headers['Authorization'] = 'Bearer $access';
    try {
      handler.resolve(await _dio.fetch(options));
    } on DioException catch (retryError) {
      handler.next(retryError);
    }
  }

  Future<String?> _refresh() async {
    final refresh = await _tokens.readRefresh();
    if (refresh == null) return null;
    try {
      final response = await _dio.post(
        '/v1/auth/refresh',
        data: {'refresh_token': refresh},
        options: Options(extra: {'skipAuth': true}),
      );
      await _tokens.save(response.data); // пишет новый refresh, обновляет access
      return response.data['access_token'] as String;
    } on DioException {
      await _tokens.clear();
      return null;
    }
  }
}
```

**Важно:** сервер ротирует refresh при каждом обновлении — новый `refresh_token`
из ответа надо сохранить, старый больше не работает.

## 4. Авторизация

| Метод | Путь | Запрос | Успех |
| --- | --- | --- | --- |
| POST | `/v1/auth/register` | `{email, password, name?, studied_language?, daily_goal_minutes?}` | `201 {user, access_token, refresh_token, expires_in}` |
| POST | `/v1/auth/login` | `{email, password}` | `200`, то же тело |
| POST | `/v1/auth/refresh` | `{refresh_token}` | `200`, новая пара |
| POST | `/v1/auth/logout` | `{refresh_token}` | `204` |
| GET | `/v1/me` | — | `200`, пользователь с профилем |
| PATCH | `/v1/me` | `{name?, studied_language?, daily_goal_minutes?}` | `200`, обновлённый профиль |

```json
{
  "user": { "id": "e381…", "email": "user@example.com", "role": "user",
            "created_at": "2026-07-28T14:18:30.172Z",
            "name": "Аня", "studied_language": "en", "daily_goal_minutes": 20 },
  "access_token": "eyJ0eXAi…",
  "refresh_token": "8f3a…",
  "expires_in": 900
}
```

Профиль (`name`, `studied_language`, `daily_goal_minutes`) опционален: задаётся
при регистрации и правится через `PATCH /v1/me` (присланные поля меняются,
пропущенные — нет, пустая строка очищает). Имя — до 100 символов,
`studied_language` — короткий код языка (сервер приводит к нижнему регистру, до
16 символов), `daily_goal_minutes` — 0..1440. Подробнее — §12.

Правила для UI:

- пароль — минимум 8 символов, проверять на клиенте до запроса;
- email нормализуется сервером (trim + lowercase), но лучше делать это и в поле
  ввода, чтобы «Вход» и «Регистрация» вели себя одинаково;
- ответ на «нет такого email» и «неверный пароль» одинаковый — показывать
  «Неверный email или пароль», не подсказывать, какие адреса зарегистрированы;
- `/v1/auth/*` ограничен 10 попытками в минуту на IP и на email: на `429`
  блокировать кнопку и показать, когда можно повторить;
- `logout` — послать `refresh_token`, затем локально почистить токены и кеш;
  ответ всегда `204`, ошибку игнорировать.

### Роли и навигация

Ролей четыре: `user`, `user-pro`, `admin`, `owner`. Роль приходит в `user.role`
и в `/v1/me`, клиент её не выбирает и не запрашивает, только читает. Владелец
задан почтой на сервере (`arovitm@gmail.com`), роли `user-pro` и `admin`
назначает owner из своей вкладки.

Нижняя навигация собирается по роли:

| Вкладка | `user` | `user-pro` | `admin` | `owner` | Что внутри |
| --- | --- | --- | --- | --- | --- |
| Уроки | да | да | да | да | каталог с сервера, фильтры (§6.1); у `user-pro` здесь же свои приватные уроки, у admin и owner — создание и правка каталога |
| Saved | да | да | да | да | локально сохранённые уроки; **пока пустой экран-заглушка** |
| Settings | да | да | да | да | учебные данные, дневная цель и прогресс (§12) |
| Управление | нет | нет | нет | да | пользователи, темы и порог пройденности (§8, §12); позже — статистика |

- `user-pro` на «Уроках» видит публичный каталог и свои приватные уроки; ему
  доступны создание и правка **только своих приватных** уроков (`is_public`
  сервер держит `false`), но не публичного каталога;
- у `admin`/`owner` создание и правка — как раньше; owner дополнительно может
  сделать урок приватным (`is_public`).

Что это значит для экранов:

- у `user` вкладка «Уроки» — только чтение: без кнопки «Добавить», без правки и
  удаления, без выбора файла. Плеер, волна и разбивка на сегменты работают
  как сейчас;
- «Saved» и «Settings» на этом шаге — пустые экраны с заголовком и заглушкой.
  Заводить их сразу стоит, чтобы навигация не переезжала потом; содержимое
  появится отдельными задачами (в «Saved» — локально сохранённые уроки);
- вкладку «Управление» показывать только при `role == 'owner'`;
- **роль — не защита, а подсказка UI**: сервер всё равно проверяет и отвечает
  `403`. Роль в токене живёт 15 минут, но сервер сверяет её с БД, поэтому только
  что выданный admin получает доступ сразу. Свою роль стоит перечитывать
  (`GET /v1/me`) при старте и при входе во вкладку — и перестраивать навигацию,
  если она изменилась или пришёл `403`.

## 5. Аудио

### 5.1 Загрузка идёт ДО создания урока

Экран «Добавить» доступен авторам уроков — `user-pro`, `admin`, `owner` — и
сохраняет текущий порядок: выбрали файл → узнали длительность → нарисовали волну
с метками → «Создать урок». Первый шаг теперь делает сервер. У обычного `user`
этого экрана нет, а `POST /v1/audio` ответит ему `403 forbidden`. Урок,
созданный `user-pro`, приватный (см. §6).

```http
POST /v1/audio
Authorization: Bearer <access>
Content-Type: multipart/form-data; boundary=…

поле: file (имя файла с расширением желательно)
```

Ответ `201` (или `200`, если такой файл уже загружался):

```json
{
  "id": "b21e…",
  "url": "http://127.0.0.1:8080/v1/audio/b21e…/file",
  "content_type": "audio/mpeg",
  "size_bytes": 2938471,
  "sha256": "3f2a…",
  "duration_ms": 183400,
  "peaks": { "resolution": 2000, "minima": "<base64 int8>", "maxima": "<base64 int8>" }
}
```

- **`duration_ms` считает сервер** — локальный замер через `just_audio`/libmpv
  (`AudioFileDataSource.resolveDurationMs`) на этом пути больше не нужен.
- Форматы: `mp3, m4a, aac, wav, flac, ogg`. Размер — до 50 МБ; проверять до
  отправки, чтобы не гонять зря трафик.
- `200` вместо `201` означает дедупликацию по `sha256`: та же запись, повторной
  обработки не было. Для клиента разницы нет.
- Загрузка длинного файла — секунды: показывать прогресс через `onSendProgress`
  и давать отмену (`CancelToken`).
- **Сразу после загрузки положить файл в кеш приложения** под ключ `audio_id`:
  он уже есть локально, качать его обратно после создания урока не нужно.

### 5.2 Пики отдаёт сервер

```http
GET /v1/audio/{id}/peaks?resolution=2000
→ { "resolution": 2000, "minima": "<base64>", "maxima": "<base64>" }
```

`resolution` в ответе — фактическое число точек. Сервер хранит огибающую в
высоком разрешении и прореживает под запрос; **повысить разрешение выше
сохранённого нельзя** — вернётся меньше точек, чем просили, это нормально,
рисовать надо по фактическому `resolution`.

Потолок — примерно 172 точки на секунду звука (внутренний блок 256 фреймов) и
4000 точек на файл. То есть для минутного и более длинного урока вы всегда
получите запрошенные 2000, а для десятисекундного отрывка — около 1700, и
виджет должен растягивать то, что пришло, а не ждать ровного числа.

Значения нормализованы так же, как сейчас на клиенте: `maxima` 0..1,
`minima` -1..0, пик прижат к единице.

```dart
List<double> decodePeaks(String encoded) {
  final bytes = base64Decode(encoded);
  final signed = bytes.buffer.asInt8List(bytes.offsetInBytes, bytes.lengthInBytes);
  return [for (final value in signed) value / 127.0];
}
```

В приложении это ровно одна новая реализация существующего интерфейса
`WaveformDataSource` — `RemoteWaveformDataSource`. Локальные реализации остаются
запасным путём для офлайна. Побочный эффект, ради которого всё и делалось: волна
выглядит одинаково на всех платформах, и на десктопе больше не нужен
`flutter_soloud`.

### 5.3 Файл: скачать один раз, играть локально

```http
GET /v1/audio/{id}/file
Authorization: Bearer <access>
→ 200, Accept-Ranges: bytes, ETag: "<sha256>", Cache-Control: private, immutable
```

**Играть по сети напрямую не нужно.** В shadowing куски зацикливаются по 2–3
секунды, и `ClippingAudioSource` поверх сетевого источника будет дёргаться на
каждом повторе. Правильный путь: при первом открытии урока файл скачивается один
раз в кеш приложения (туда же, где сейчас лежит аудио), а плеер как и сегодня
работает с `AudioSource.file`.

- Ссылка требует заголовок `Authorization` — отдать её напрямую плееру или
  `Image.network`-подобному виджету нельзя, качать через `dio.download`.
- Поддерживается `Range`: обрыв докачивается заголовком
  `Range: bytes=<уже скачано>-`, ответ `206` с `Content-Range`.
- Целостность проверять по `sha256` из ответа `POST /v1/audio` или из
  `lesson.audio.sha256`: не совпало — файл удалить и скачать заново.
- Имя в кеше — `audio_id` (+ расширение из `content_type`). Файл иммутабелен:
  содержимое под одним `audio_id` не меняется никогда, инвалидация не нужна.
- Чистка кеша — по LRU и при удалении уроков; **осторожно: один `audio_id` может
  быть у нескольких уроков** (дедупликация по `sha256`), удалять файл только
  когда на него не ссылается ни один живой урок.

## 6. Уроки

```json
{
  "id": "9f1c…",
  "title": "TED: How to learn",
  "duration_ms": 183400,
  "created_at": "2026-07-28T10:00:00.000Z",
  "updated_at": "2026-07-28T10:12:03.000Z",
  "deleted_at": null,
  "version": 3,
  "accent": "US",
  "level": "b1",
  "is_public": true,
  "topic": { "id": "4450…", "name": "Education" },
  "audio": { "id": "b21e…", "url": "…/v1/audio/b21e…/file", "content_type": "audio/mpeg",
             "size_bytes": 2938471, "sha256": "3f2a…", "duration_ms": 183400 },
  "segments": [
    { "index": 0, "text": "Hello there.", "start_ms": 0, "end_ms": 2100 },
    { "index": 1, "text": "How are you?", "start_ms": 2100, "end_ms": 4300 }
  ]
}
```

| Метод | Путь | Роль | Смысл |
| --- | --- | --- | --- |
| GET | `/v1/lessons?since=&limit=&cursor=` | любая | публичные + свои приватные, `updated_at desc` |
| GET | `/v1/lessons/{id}` | любая | один урок (свой приватный или публичный), `ETag: "<version>"` |
| PUT | `/v1/lessons/{id}` | автор | создать (`201`) или обновить (`200`) |
| DELETE | `/v1/lessons/{id}` | автор | мягкое удаление, `204` |

Публичный каталог общий: admin и owner правят и удаляют любой публичный урок.
Приватный урок правит и удаляет только его автор (`user-pro` — свои, owner —
любые). Для того, кому создание/правка недоступны, `PUT`/`DELETE` — `403
forbidden`; такие кнопки показывать не нужно.

Поле `is_public` в теле урока — видимость. В `PUT` его учитывает только owner
(по умолчанию `true`): у `user-pro` урок всегда приватный, у `admin` — всегда
публичный, независимо от присланного значения. При правке видимость меняет лишь
owner; у остальных она сохраняется. Приватный чужой урок неотличим от
несуществующего — `404` в списке и по id.

### Создание урока

```http
PUT /v1/lessons/<uuid, сгенерированный клиентом>
Content-Type: application/json

{ "title": "TED: How to learn",
  "audio_id": "b21e…",
  "created_at": "2026-07-28T10:00:00.000Z",
  "accent": "US",
  "level": "b1",
  "topic_id": "4450…",
  "segments": [ { "index": 0, "text": "…", "start_ms": 0, "end_ms": 2100 }, … ] }
```

`PUT`, а не `POST`, потому что UUID генерит клиент: повтор после потери сети не
создаёт дубль. `duration_ms` присылать не нужно — сервер берёт длительность
аудио; если прислать и не совпадёт, будет `422`.

### Категории: акцент, уровень, тема

Три поля, которые заполняются на экране создания урока и по которым потом
фильтруется каталог (§6.1).

| Поле | Значения | На экране создания |
| --- | --- | --- |
| `accent` | `US`, `UK` | обязательный выбор, значения зашиты в клиенте |
| `level` | `a1`, `a2`, `b1`, `b2`, `c1`, `c2` | обязательный выбор, значения зашиты в клиенте |
| `topic_id` | id из `GET /v1/topics` | необязательный; не выбрали — сервер поставит «Other» |

- `accent` и `level` — закрытые списки: сервер меняет их только релизом, поэтому
  их можно держать `enum`-ом в клиенте и не ходить за ними по сети. Пустое или
  неизвестное значение — `422` с текстом, что ожидалось;
- **темы — справочник с сервера**, их правит owner, поэтому список нужно
  запрашивать (`GET /v1/topics`), а не хардкодить. Кешировать можно, но
  обновлять при входе на экран создания и в фильтры: тему могли переименовать
  или удалить;
- в ответе урока тема приходит объектом `{id, name}` — второй запрос ради
  названия не нужен. Название может измениться, id — нет: в кеше и в фильтрах
  опирайтесь на `topic.id`;
- удалённая тема не ломает уроки: они переезжают на «Other», и очередной `GET`
  вернёт их уже с новой темой.

**Инварианты, которые сервер проверяет** (те же, что в домене приложения, — не
дайте им разойтись):

- сегментов ≥ 1, `index` идут `0..N-1` без дыр;
- границы строго возрастают и идут встык: `segments[i].start_ms == segments[i-1].end_ms`;
- `segments[0].start_ms == 0`, `segments[N-1].end_ms == duration_ms` аудио;
- `audio_id` доступен редактору: либо он его и загрузил, либо файл уже
  опубликован в живом уроке (иначе `404`).

Проверять это на клиенте до отправки: пользователь должен получать ошибку от
редактора меток, а не от сети.

### Правка урока

Тот же `PUT`, сегменты приходят **целиком** — это агрегат (ровно так же работает
`LessonLocalDataSource.upsertLesson` и use case `UpdateLessonContent`). При
обновлении обязателен заголовок:

```http
If-Match: "3"
```

Версию брать из `lesson.version` (или из `ETag` последнего `GET`). Без заголовка
или с устаревшей версией — `409 version_conflict`, актуальный урок лежит в
`error.current`:

```json
{ "error": { "code": "version_conflict", "message": "version conflict",
             "current": { "id": "9f1c…", "version": 4, "segments": [ … ] } } }
```

Для приложения на одного пользователя это редкость (два устройства правят один
урок). Достаточно: записать `current` в кеш, показать «урок изменён на другом
устройстве» и предложить повторить правку поверх свежей версии. Молча
перезаписывать чужую версию нельзя.

Обновление снимает мягкое удаление: `PUT` по удалённому уроку восстанавливает его.

### Удаление

`DELETE` — мягкое: урок остаётся с `deleted_at` и повышенной `version`, чтобы
удаление разошлось по устройствам. Локально запись убирать сразу. Повторный
`DELETE` того же урока — `204`, чужой или несуществующий — `404`.

### 6.1 Фильтры каталога

```http
GET /v1/lessons?accent=UK&level=c1&topic_id=4450…&limit=50
```

Все три параметра необязательны и складываются по «и». Значения — те же, что
в теле урока; регистр не важен, мусор — `422`, а не пустой список. Пагинация
работает как обычно: `next_cursor` уже учитывает фильтры, но при смене фильтров
курсор нужно сбрасывать.

**Для синхронизации кеша фильтры не передавать.** `since`-дельта с фильтром
неполна: урок, у которого сменили тему или уровень, из выборки выпадет, и клиент
не узнает, что он изменился. Правильный порядок — тянуть дельту без фильтров
в кеш, а фильтровать уже локально; серверные фильтры нужны там, где каталог
большой и грузится страницами.

### 6.2 Папки

Папка — авторская подборка уже созданных уроков (серия, курс, «моё на потом»).
Сценарий: пользователь загрузил несколько уроков и решает сгруппировать часть из
них в папку. Заводят папки те же роли, что и уроки (`user-pro`, `admin`, `owner`),
и по тем же правилам доступа и видимости, что уроки (§6): публичную ведут `admin`
и `owner` и видят все, приватную видит только автор; `user-pro` — всегда
приватные, `admin` — всегда публичные, owner — по `is_public`.

```json
{
  "id": "7a2c…",
  "title": "TED-разговорный",
  "is_public": true,
  "created_at": "2026-08-30T10:00:00.000Z",
  "updated_at": "2026-08-30T10:12:03.000Z",
  "deleted_at": null,
  "version": 2,
  "lesson_count": 2,
  "lessons": [ { … урок как в §6 … } ]
}
```

| Метод | Путь | Роль | Смысл |
| --- | --- | --- | --- |
| GET | `/v1/folders?since=&limit=&cursor=` | любая | публичные + свои приватные, `updated_at desc`; в списке только `lesson_count`, без `lessons` |
| GET | `/v1/folders/{id}` | любая | папка с её уроками, `ETag: "<version>"` |
| PUT | `/v1/folders/{id}` | автор | создать (`201`) или обновить (`200`): `{title, created_at?, is_public?}` |
| DELETE | `/v1/folders/{id}` | автор | мягкое удаление, `204` |
| POST | `/v1/folders/{id}/lessons` | автор | `{lesson_ids: […]}` — добавить уроки → обновлённая папка |
| DELETE | `/v1/folders/{id}/lessons/{lesson_id}` | автор | убрать урок из папки, `204` |

- **UUID папки генерит клиент**, создание идёт через `PUT /v1/folders/{id}` (как
  у уроков — идемпотентно); `POST /v1/folders` не поддержан;
- список папок в детали (`lessons`) приходит только там, где мы их выбрали
  (детали, создание/правка, изменение состава). В списке (`GET /v1/folders`) —
  лишь `lesson_count`, а сами уроки тяните по `GET /v1/folders/{id}` при открытии;
- **правка метаданных (название, видимость) требует `If-Match: "<version>"`** —
  как у уроков, при устаревшей версии `409` с `error.current`. А вот
  добавление/удаление уроков `If-Match` не требует (операция аддитивна и
  идемпотентна), но поднимает `version` папки — чтобы состав разошёлся дельтой;
- **в папку кладут только доступные редактору уроки** (публичные или свои
  приватные): недоступный — `404`. Повторно добавить тот же урок — не ошибка;
- папка показывает лишь уроки, **видимые зрителю**, в порядке добавления: если в
  публичную папку добавить приватный урок, чужой пользователь его в ней не
  увидит, а `lesson_count` отражает видимое зрителю число;
- удаление урока (`DELETE /v1/lessons/{id}`) само убирает его из всех папок;
  удаление папки уроки не трогает — это лишь снятие группировки;
- синхронизировать папки как уроки (§7): дельта по `since` без фильтров, записи
  с `deleted_at` — из кеша.

### 6.3 Лента библиотеки: корень одним запросом

Главный экран — это корень: папки и уроки, которые ни в одной папке не лежат.
Собирать его на клиенте из `/v1/lessons` и `/v1/folders` **не нужно**: два списка
приходят вразнобой, и уроки из папок успевают мелькнуть в списке и исчезнуть.
Корень отдаётся готовым.

```http
GET /v1/library?limit=50
```

```json
{
  "items": [
    { "type": "folder", "id": "7a2c…", "title": "TED-разговорный", "lesson_count": 2, … },
    { "type": "lesson", "id": "9f1c…", "title": "Одиночный урок", … }
  ],
  "next_cursor": null
}
```

- `type` — `"folder"` или `"lesson"`. Тело папки такое же, как в `GET /v1/folders`
  (с `lesson_count`, без `lessons`), тело урока — как в `GET /v1/lessons`;
- открыли папку — тянем её уроки по `GET /v1/folders/{id}` (§6.2);
- сортировка `updated_at desc`, курсор общий для обеих половин: `limit` и
  `cursor`/`next_cursor` работают как везде (§7);
- урок скрыт из корня, только если лежит в папке, **видимой зрителю**: чужая
  приватная папка урок не прячет, мягко удалённая — тоже;
- **с фильтром** (`accent`/`level`/`topic_id`) лента становится плоским поиском
  по урокам: папки не приходят (у них нет ни акцента, ни уровня), а уроки внутри
  папок — приходят, иначе фильтр бы их не нашёл;
- **`since` не поддержан** — `422`. Это экран, а не источник синхронизации:
  состав папки живёт отдельно от урока и `version` урока не поднимает, поэтому
  «урок положили в папку» дельтой по урокам не выражается. Кеш наполняют
  `GET /v1/lessons?since=` и `GET /v1/folders?since=` (§7), а корень рисуют по
  `/v1/library` — сеть в приоритете, кеш как запасной вариант.

## 7. Синхронизация и кеш

Схема намеренно простая, и её стоит держать простой, чтобы не скатиться в
offline-first раньше времени:

- **сервер — источник истины**, sqflite становится кешем для чтения; каталог
  общий, поэтому кеш у всех ролей наполняется одинаково — чужие уроки в нём
  нормальны, а `user` только читает;
- на старте и по pull-to-refresh: `GET /v1/lessons?since=<последний известный
  updated_at>` → применить дельту, записи с непустым `deleted_at` удалить из кеша
  вместе с осиротевшим аудио;
- **без `since`** список отдаёт только живые уроки; **с `since`** — дельту,
  включая удалённые. Это единственное различие, и оно важно: первый запуск делать
  без `since`;
- сохранять новый «водяной знак» — максимальный `updated_at` из полученных
  записей, а не текущее время устройства (часы могут врать);
- запись (создание, правка, удаление) доступна только `admin` и `owner`, идёт на
  сервер, при успехе — в кеш; нет сети — честная ошибка в UI, как сейчас при
  сбое БД;
- аудио кешируется по `audio_id`, чистка — по LRU и по удалённым урокам.

Пагинация: `limit` (по умолчанию 50, максимум 200) и `cursor` из `next_cursor`
предыдущего ответа. `next_cursor: null` — страниц больше нет. Курсор — строка
base64, при подстановке в query её нужно url-энкодить (`Uri.encodeQueryComponent`).

```json
{ "items": [ { … урок … } ], "next_cursor": "MjAyNi0wNy0yOFQxMDoxMjowMy4wMDBafDlmMWM…" }
```

Полноценная офлайн-очередь (`pending_operations`, разрешение конфликтов,
дозагрузка) — отдельный этап, и он нужен только если правка уроков без сети
действительно требуется. Швы для него уже есть: `version`/`If-Match` и мягкое
удаление.

## 8. Вкладка owner: пользователи и темы

Отдельная вкладка нижней навигации, видна только при `role == 'owner'`. Сейчас
на ней два раздела — пользователи (роли и удаление) и справочник тем; позже сюда
же добавится статистика, так что экран стоит делать с запасом под несколько
блоков.

### 8.1 Пользователи

| Метод | Путь | Запрос → ответ |
| --- | --- | --- |
| GET | `/v1/admin/users?q=&limit=&offset=` | → `{users: [{id, email, role, created_at}], total, limit, offset}` |
| PATCH | `/v1/admin/users/{id}/role` | `{ "role": "user" \| "user-pro" \| "admin" \| "owner" }` → обновлённый пользователь |
| DELETE | `/v1/admin/users/{id}` | → `204` |

- `q` — подстрока email, регистр не важен; `limit` до 200, `offset` для страниц.
- Роль в access-токене живёт до 15 минут, а сервер сверяет её с базой: только что
  назначенный admin получает доступ сразу, не дожидаясь нового токена.
- Понизить или удалить владельца, заданного в конфигурации сервера, нельзя —
  `422`. Кнопки «сделать user» и «удалить» для него лучше не показывать вовсе;
  удалить самого себя тоже нельзя.
- **Удаление необратимо и уносит сессии пользователя** — спрашивать
  подтверждение с вводом email или явной кнопкой «Удалить навсегда». Публичный
  каталог при этом не страдает: публичные уроки и папки удалённого переходят к
  owner. А вот его приватные уроки, папки и их аудио удаляются вместе с ним —
  это личное, а не общее, и в чужие руки не переходит.
- Своя роль в `/v1/me` может измениться в любой момент: перечитывать её при
  входе во вкладку и прятать раздел на `403`.

### 8.2 Темы

Справочник тем урока. Читать его может любой (он нужен в фильтрах и на экране
создания), а править — только owner.

| Метод | Путь | Запрос → ответ |
| --- | --- | --- |
| GET | `/v1/topics` | → `{topics: [{id, name, is_default, created_at}]}` |
| POST | `/v1/topics` | `{name}` → `201`, созданная тема |
| PATCH | `/v1/topics/{id}` | `{name}` → `200`, обновлённая тема |
| DELETE | `/v1/topics/{id}` | → `204` |

- список приходит отсортированным: обычные темы по алфавиту, `is_default`
  («Other») — последней. Этот же порядок годится и для выпадающего списка;
- имя — до 60 символов, уникально без учёта регистра; пустое имя и повтор
  дают `422` с готовым текстом для показа;
- **удалять тему безопасно**: её уроки переезжают на «Other», а не пропадают.
  Но об этом стоит предупредить в диалоге — админ должен понимать, что разметка
  части каталога изменится. После удаления перечитать список уроков;
- у темы с `is_default: true` кнопку «Удалить» не показывать — сервер ответит
  `422`. Переименовать её можно;
- после любой правки обновить кеш тем: он используется в фильтрах каталога.

## 9. Обработка ошибок в UI

Единый разбор в `ApiClient`: тело ошибки → `ApiException(code, message, status,
details)`. Дальше по слоям идёт `ApiException`, а не `DioException`.

- сетевые сбои (`DioExceptionType.connectionError/timeouts`) — «нет связи с
  сервером», кнопка «Повторить»; это не то же самое, что ошибка API;
- `unauthorized` обрабатывается интерсептором и наверх выходит только когда
  refresh не удался — тогда выход на `/login`;
- `not_found` при открытии урока — удалить из кеша и показать «урок удалён»;
- `version_conflict` — сценарий §6, не общий тост;
- `payload_too_large` / `unsupported_media_type` — проверять до отправки, но
  сообщение с сервера всё равно показывать (в нём причина);
- `rate_limited` — заблокировать форму входа на минуту.

## 10. Тестирование

- `LessonRemoteDataSource`, `AudioRemoteDataSource`, `AuthRepository` — за
  интерфейсами; репозиторий и контроллеры тестируются на подделках без сети.
- `dio` мокать через `DioAdapter`/`http_mock_adapter` — проверить: подстановку
  `Authorization`, единственный refresh на несколько параллельных 401, выход при
  401 на refresh, разбор всех кодов ошибок из §1.
- Отдельный тест на `decodePeaks`: base64 int8 → `-1..1`, длина равна
  `resolution` из ответа.
- Тест на конфликт: `PUT` без `If-Match` → 409 → в кеше оказывается `current`.
- Контрактные тесты сервера уже есть (`cargo test`, 33 штуки) — при расхождении
  поведения сначала смотреть в них, они описывают ожидаемые статусы и тела.
- Отдельно проверить сборку навигации по роли: три варианта `user.role` дают три
  набора вкладок, а `403` от сервера приводит UI в соответствие.

## 11. Порядок работ

Каждый этап оставляет приложение в рабочем состоянии.

1. **Сеть и токены.** `ApiClient`, `TokenStorage`, интерсепторы, `ApiException`.
   Проверяется на `/healthz` и `/v1/me`.
2. **Авторизация.** Фича `auth`, экраны входа и регистрации, `redirect` в
   роутере, автологин по refresh на старте. Уроки на этом шаге ещё локальные.
3. **Навигация по ролям.** Нижние вкладки «Уроки», «Saved», «Settings» для всех
   и «Пользователи» для owner (§4). «Saved» и «Settings» — заглушки; у `user`
   на «Уроках» нет создания, правки и удаления.
4. **Аудио.** `POST /v1/audio` на экране создания (с прогрессом и отменой),
   `RemoteWaveformDataSource`, кеш файла по `audio_id`. Здесь же выравнивается
   поведение волны на всех платформах и убирается локальный замер длительности.
5. **Уроки.** `LessonRemoteDataSource`, сборка репозитория «сервер + кеш»,
   докачивание аудио при открытии урока, `If-Match` при правке. Здесь же —
   выбор акцента, уровня и темы на экране создания (§6, «Категории»).
6. **Дельта-синхронизация** по `since`, чистка кеша, pull-to-refresh.
7. **Фильтры каталога** по акценту, уровню и теме (§6.1).
8. **Вкладка «Управление»** для `owner`: пользователи и справочник тем (§8).
9. **Потом, по необходимости:** содержимое «Saved» и «Settings», статистика во
   вкладке owner, офлайн-очередь записи, вход через Apple/Google (обязателен для
   iOS, если появится вход через соцсети).

### Чек-лист приёмки

- [ ] после перезапуска приложение входит само по refresh из secure storage;
- [ ] протухший access молча обновляется, пользователь ничего не замечает;
- [ ] refresh-токен после каждого обновления перезаписан новым;
- [ ] выход чистит токены, кеш уроков и аудиофайлы;
- [ ] загрузка 50 МБ показывает прогресс и отменяется;
- [ ] повторная загрузка того же файла не качает его второй раз (ответ `200`);
- [ ] волна рисуется по серверным пикам одинаково на Android, iOS, Windows;
- [ ] урок создаётся одним `PUT`, повтор при обрыве не создаёт дубль;
- [ ] правка с устаревшей версией показывает «изменён на другом устройстве»;
- [ ] удалённый на другом устройстве урок исчезает после pull-to-refresh;
- [ ] аудио играет из локального файла, зацикливание кусков не дёргается;
- [ ] у `user` видны три вкладки: «Уроки», «Saved», «Settings»; «Saved» и
      «Settings» открываются пустыми и не падают;
- [ ] у `user` на «Уроках» нет создания, правки и удаления, а урок, заведённый
      админом, виден и играется;
- [ ] `admin` создаёт и правит уроки, но вкладки «Управление» у него нет;
- [ ] вкладка «Управление» видна только owner и переживает `403` без падения;
- [ ] удаление пользователя спрашивает подтверждение, а его уроки остаются
      в каталоге;
- [ ] урок нельзя создать без акцента и уровня, а без темы — можно, и он
      получает «Other»;
- [ ] фильтры по акценту, уровню и теме складываются и сбрасывают пагинацию;
- [ ] тема, созданная owner, сразу доступна в фильтрах и на экране создания;
- [ ] после удаления темы её уроки показываются с «Other», а не пропадают;
- [ ] урок, созданный `user-pro`, приватный: у автора виден и играется, у чужого
      — `404` и в списке, и по ссылке;
- [ ] owner может пометить урок приватным (`is_public: false`), и его перестают
      видеть остальные;
- [ ] профиль (имя, язык, цель) сохраняется при регистрации и правится в
      «Settings» через `PATCH /v1/me`;
- [ ] прогресс копит минуты и повторы, «пройдено» не удваивается, динамика
      берётся из `GET /v1/progress/history`.

## 12. Профиль, прогресс и настройки

### 12.1 Профиль (учебные данные)

Поля `name`, `studied_language`, `daily_goal_minutes` приходят в объекте `user`
(ответы auth и `GET /v1/me`). Задаются при регистрации и правятся в «Settings»:

```http
PATCH /v1/me            { "name": "Anna", "studied_language": "en", "daily_goal_minutes": 30 }
→ 200  { …, "name": "Anna", "studied_language": "en", "daily_goal_minutes": 30 }
```

- присланные поля меняются, пропущенные — нет; пустая строка очищает поле;
- имя — до 100 символов; `studied_language` — короткий код (сервер приводит к
  нижнему регистру, до 16 символов); `daily_goal_minutes` — 0..1440, иначе `422`;
- изучаемый язык и дневную цель показывать в «Settings» и на экране прогресса.

### 12.2 Прогресс

Прогресс есть у любого авторизованного пользователя. Клиент батчит активность и
шлёт её событиями; «пройден ли урок» решает **клиент** (порог повторов сегмента —
лишь подсказка сервера, см. §12.3).

| Метод | Путь | Тело / ответ |
| --- | --- | --- |
| POST | `/v1/progress/events` | `{listened_ms?, segment_repeats?, lesson_id?, completed?}` → свежая сводка |
| GET | `/v1/progress` | сводка |
| GET | `/v1/progress/history?days=30` | `{days: [{day, listened_ms, segment_repeats}]}` за окно (1..365) |

```json
{ "today": { "day": "2026-08-06", "listened_ms": 180000, "segment_repeats": 10 },
  "totals": { "listened_ms": 180000, "segment_repeats": 10, "lessons_completed": 1 },
  "week_minutes": 3,
  "week": [ { "day": "2026-08-06", "listened_ms": 180000, "segment_repeats": 10 } ],
  "recent_lesson_ids": ["9f1c…"],
  "daily_goal_minutes": 20,
  "completion_reps": 10 }
```

- шлите событие периодически: `listened_ms` — прослушано с прошлого отчёта,
  `segment_repeats` — сделано повторов сегментов; сервер копит их за день (UTC);
- `lesson_id` в событии добавляет урок в «последние 5» (`recent_lesson_ids`);
  учитывается только видимый урок (публичный или свой приватный), иначе `404`;
- когда клиент по своему счётчику решил, что каждый сегмент повторён нужное число
  раз (`completion_reps`), пошлите `completed: true` с `lesson_id`. Отметка
  ставится один раз — повторная отправка счётчик пройденных не удваивает;
- `week` — последние 7 дней для графика динамики, `week_minutes` — сумма минут за
  них; полную историю для длинных графиков берите из `history`;
- `daily_goal_minutes` в сводке дублирует профиль — удобно рисовать «сегодня X из
  цели» без второго запроса.

### 12.3 Настройки (порог пройденности)

| Метод | Путь | Роль | Тело / ответ |
| --- | --- | --- | --- |
| GET | `/v1/settings` | любая | `{ "lesson_completion_reps": 10 }` |
| PATCH | `/v1/settings` | owner | `{ "lesson_completion_reps": 15 }` (1..1000) → текущие настройки |

`lesson_completion_reps` — сколько раз надо повторить каждый сегмент, чтобы урок
считался пройденным. Значение ведёт owner (вкладка «Управление»), читают все:
клиент берёт его как цель для прогресс-бара урока и сам решает, когда слать
`completed`. Оно же приходит в сводке прогресса как `completion_reps`.
