# The Shado client: what to do and how

A specification for the server as already implemented (see
[README](../README.md)). The domain and presentation of the app do not change —
on one condition: **the repository keeps returning `Lesson.audioPath` as a local
path to a file that is ready to play**, only now it downloads that file when
needed. Then the player, the waveform and every screen stay as they are.

The order of work is at the end of the document (§11), together with the
acceptance checklist.

---

## 1. General API rules

- The base is `http://127.0.0.1:8080` locally and `https://…` in production. All
  the paths below start at the root, with the version in the path: `/v1/...`.
- Request and response bodies are JSON, `snake_case`, encoded in UTF-8.
- Times are ISO-8601 UTC with milliseconds: `2026-07-28T10:00:00.000Z`. In Dart:
  `DateTime.parse(...)` and `dt.toUtc().toIso8601String()`.
- All durations and positions are integer milliseconds.
- Authorization: `Authorization: Bearer <access_token>` on every path except
  `/healthz` and `/v1/auth/*`.
- Identifiers are UUID v4 as strings. **The lesson UUID is generated by the
  client** (as it already is in `LessonRepositoryImpl`), the audio UUID by the
  server.

### The error format

One for the whole API:

```json
{ "error": { "code": "validation_error", "message": "первый сегмент должен начинаться с 0" } }
```

| code | HTTP | When | What the client does |
| --- | --- | --- | --- |
| `validation_error` | 422 | the body failed a check (segments, email, password) | show `message`, do not repeat the request |
| `invalid_credentials` | 401 | a wrong email/password pair | "wrong email or password" |
| `email_taken` | 409 | the email is already registered | offer to sign in |
| `unauthorized` | 401 | no token, an expired token, or an invalid refresh | see §3, refresh the token or sign out |
| `forbidden` | 403 | the role is not enough: editing the catalog or the owner tab | hide the action, do not repeat |
| `not_found` | 404 | there is no such resource, it was deleted **or it is not published yet** | treat as "deleted on the server" |
| `version_conflict` | 409 | an edit on top of a stale version | see §6, `error.current` holds the current lesson |
| `payload_too_large` | 413 | the file is over the limit (50 MB) | state the limit before uploading |
| `unsupported_media_type` | 415 | the format is unsupported or the file is unreadable | the list of formats is in the message |
| `rate_limited` | 429 | more than 10 attempts a minute on `/v1/auth/*` | wait a minute, show a timer |
| `internal_error` | 500 | a server failure | "try later", log it |

A rule for the future: **an unknown `code` is not "all good"**. Map by the list
and treat everything else as a generic error by the HTTP status.

### The catalog and privacy

**The public catalog.** Public lessons are curated by `admin` and `owner` and
seen by every authorized user: the list of public ones is the same for everyone.
The audio of a public lesson is readable by everyone.

**Private lessons.** A `user-pro` keeps their own private lessons (always
private), and the owner can create private ones alongside public ones. A private
lesson and its audio are seen by the author only: it is absent from anyone
else's list, and a direct link gives a `404`, as for something that does not
exist. Visibility is carried by the `is_public` field in the lesson body (§6).

An editor's unfinished work is private too: a fresh `POST /v1/audio` upload is
visible only to whoever made it, until a live lesson references it. An
unavailable resource gives a `404` (it does not exist, is not published yet, or
is someone else's private one), and an attempt to change the catalog without the
role gives a `403`. On a `404` the record is removed from the local cache; on a
`403` the button is hidden — repeating the request is pointless.

## 3. Tokens and the network layer

**Storage.** The refresh token goes into `flutter_secure_storage` only, and the
access token stays in memory (it has no reason to survive a restart, it lives 15
minutes).

**The lifecycle.**

1. `register`/`login` → save `refresh_token` into secure storage and keep
   `access_token` in a field of `ApiClient`.
2. App start: there is a refresh token → call `POST /v1/auth/refresh` right away
   and get the access token and the user data; there is none, or the answer is a
   401 → the sign-in screen.
3. Any 401 with `code: unauthorized` on an ordinary request → a single
   concurrent refresh request, with the rest waiting for it and being retried.
4. A 401 on the refresh itself → a full sign-out: clear the secure storage, the
   local lesson and audio caches, and go to `/login`.

Point 4 is mandatory: the server revokes the **entire chain** of refresh tokens
when an already used one arrives (a sign of theft). Retrying silently is
pointless.

```dart
class AuthInterceptor extends Interceptor {
  AuthInterceptor(this._dio, this._tokens);

  final Dio _dio;
  final TokenStorage _tokens;
  Future<String?>? _refreshing; // one refresh for all parallel requests

  @override
  void onRequest(RequestOptions options, RequestInterceptorHandler handler) {
    final access = _tokens.access;
    if (access != null && options.extra['skipAuth'] != true) {
      options.headers['Authorization'] = 'Bearer $access';
    }
    handler.next(options);
  }

  @override
  Future<void> onError(DioException err, ErrorInterceptorHandler handler) async {
    final isAuthCall = err.requestOptions.path.startsWith('/v1/auth/');
    if (err.response?.statusCode != 401 || isAuthCall) return handler.next(err);

    final access = await (_refreshing ??= _refresh().whenComplete(() => _refreshing = null));
    if (access == null) return handler.next(err); // AuthRepository initiates the sign-out

    final options = err.requestOptions..headers['Authorization'] = 'Bearer $access';
    try {
      handler.resolve(await _dio.fetch(options));
    } on DioException catch (retryError) {
      handler.next(retryError);
    }
  }

  Future<String?> _refresh() async {
    final refresh = await _tokens.readRefresh();
    if (refresh == null) return null;
    try {
      final response = await _dio.post(
        '/v1/auth/refresh',
        data: {'refresh_token': refresh},
        options: Options(extra: {'skipAuth': true}),
      );
      await _tokens.save(response.data); // writes the new refresh, updates the access
      return response.data['access_token'] as String;
    } on DioException {
      await _tokens.clear();
      return null;
    }
  }
}
```

**Important:** the server rotates the refresh token on every refresh — the new
`refresh_token` from the response must be saved, and the old one stops working.

## 4. Authorization

| Method | Path | Request | Success |
| --- | --- | --- | --- |
| POST | `/v1/auth/register` | `{email, password, name?, studied_language?, daily_goal_minutes?}` | `201 {user, access_token, refresh_token, expires_in}` |
| POST | `/v1/auth/login` | `{email, password}` | `200`, the same body |
| POST | `/v1/auth/refresh` | `{refresh_token}` | `200`, a new pair |
| POST | `/v1/auth/logout` | `{refresh_token}` | `204` |
| GET | `/v1/me` | — | `200`, the user with their profile |
| PATCH | `/v1/me` | `{name?, studied_language?, daily_goal_minutes?}` | `200`, the updated profile |

```json
{
  "user": { "id": "e381…", "email": "user@example.com", "role": "user",
            "created_at": "2026-07-28T14:18:30.172Z",
            "name": "Anna", "studied_language": "en", "daily_goal_minutes": 20 },
  "access_token": "eyJ0eXAi…",
  "refresh_token": "8f3a…",
  "expires_in": 900
}
```

The profile (`name`, `studied_language`, `daily_goal_minutes`) is optional: it
is set at registration and edited through `PATCH /v1/me` (the fields that are
sent change, the omitted ones do not, and an empty string clears one). The name
is up to 100 characters, `studied_language` is a short language code (the server
lowercases it, up to 16 characters), and `daily_goal_minutes` is 0..1440. More
in §12.

The rules for the UI:

- the password is at least 8 characters, checked on the client before the
  request;
- the email is normalized by the server (trim + lowercase), but it is better to
  do it in the input field too, so that "Sign in" and "Register" behave the
  same;
- the answer to "no such email" and to "wrong password" is the same — show
  "wrong email or password" and do not hint at which addresses are registered;
- `/v1/auth/*` is limited to 10 attempts a minute per IP and per email: on a
  `429` lock the button and show when it may be retried;
- `logout` sends the `refresh_token`, then clears the tokens and the cache
  locally; the answer is always `204` and an error is ignored.

### Roles and navigation

There are four roles: `user`, `user-pro`, `admin`, `owner`. The role arrives in
`user.role` and in `/v1/me`; the client neither chooses nor requests it, it only
reads it. The owner is set by email on the server (`arovitm@gmail.com`), and the
`user-pro` and `admin` roles are granted by the owner from their own tab.

The bottom navigation is assembled by role:

| Tab | `user` | `user-pro` | `admin` | `owner` | What is inside |
| --- | --- | --- | --- | --- | --- |
| Lessons | yes | yes | yes | yes | the catalog from the server, the filters (§6.1); a `user-pro` also has their own private lessons here, and admin and owner have catalog creation and editing |
| Saved | yes | yes | yes | yes | locally saved lessons; **an empty placeholder screen for now** |
| Settings | yes | yes | yes | yes | study data, the daily goal and progress (§12) |
| Management | no | no | no | yes | users, topics and the completion threshold (§8, §12); statistics later |

- on "Lessons" a `user-pro` sees the public catalog plus their own private
  lessons; they may create and edit **their own private lessons only**
  (the server keeps `is_public` at `false`), but not the public catalog;
- for `admin`/`owner` creation and editing work as before, and the owner may
  additionally make a lesson private (`is_public`).

What that means for the screens:

- for a `user` the "Lessons" tab is read-only: no "Add" button, no editing or
  deletion, no file picking. The player, the waveform and the segment
  breakdown work as they do now;
- "Saved" and "Settings" are empty screens with a title and a placeholder at
  this step. It is worth creating them right away so that the navigation does
  not move later; the content comes as separate tasks (in "Saved", the locally
  saved lessons);
- show the "Management" tab only when `role == 'owner'`;
- **the role is a UI hint, not a protection**: the server checks anyway and
  answers `403`. The role in the token lives 15 minutes, but the server verifies
  it against the database, so a freshly promoted admin gets access immediately.
  It is worth re-reading your own role (`GET /v1/me`) on start and on entering
  the tab — and rebuilding the navigation if it changed or a `403` arrived.

## 5. Audio

### 5.1 The upload happens BEFORE the lesson is created

The "Add" screen is available to lesson authors — `user-pro`, `admin`, `owner` —
and keeps the current order: pick a file → find out the duration → draw the
waveform with markers → "Create lesson". The first step is now done by the
server. A plain `user` does not have this screen, and `POST /v1/audio` answers
them with a `403 forbidden`. A lesson created by a `user-pro` is private (see
§6).

```http
POST /v1/audio
Authorization: Bearer <access>
Content-Type: multipart/form-data; boundary=…

field: file (a file name with an extension is preferable)
```

A `201` response (or a `200` if such a file was uploaded before):

```json
{
  "id": "b21e…",
  "url": "http://127.0.0.1:8080/v1/audio/b21e…/file",
  "content_type": "audio/mpeg",
  "size_bytes": 2938471,
  "sha256": "3f2a…",
  "duration_ms": 183400,
  "peaks": { "resolution": 2000, "minima": "<base64 int8>", "maxima": "<base64 int8>" }
}
```

- **`duration_ms` is computed by the server** — the local measurement through
  `just_audio`/libmpv (`AudioFileDataSource.resolveDurationMs`) is no longer
  needed on this path.
- The formats are `mp3, m4a, aac, wav, flac, ogg`. The size is up to 50 MB;
  check it before sending so as not to waste traffic.
- A `200` instead of a `201` means deduplication by `sha256`: the same record,
  with no repeated processing. It makes no difference to the client.
- Uploading a long file takes seconds: show the progress through
  `onSendProgress` and allow cancellation (`CancelToken`).
- **Put the file into the app cache right after the upload** under the
  `audio_id` key: it is already there locally, and there is no need to download
  it back after the lesson is created.

### 5.2 The peaks come from the server

```http
GET /v1/audio/{id}/peaks?resolution=2000
→ { "resolution": 2000, "minima": "<base64>", "maxima": "<base64>" }
```

The `resolution` in the response is the actual number of points. The server
stores the envelope at a high resolution and thins it out for the request;
**raising the resolution above the stored one is impossible** — fewer points
than asked for come back, which is normal, and drawing must follow the actual
`resolution`.

The ceiling is about 172 points per second of sound (an internal block of 256
frames) and 4000 points per file. So for a lesson of a minute or longer you
always get the requested 2000, while a ten-second excerpt gives around 1700, and
the widget must stretch whatever arrived rather than expect a round number.

The values are normalized the same way as on the client today: `maxima` 0..1,
`minima` -1..0, with the peak pinned to one.

```dart
List<double> decodePeaks(String encoded) {
  final bytes = base64Decode(encoded);
  final signed = bytes.buffer.asInt8List(bytes.offsetInBytes, bytes.lengthInBytes);
  return [for (final value in signed) value / 127.0];
}
```

In the app this is exactly one new implementation of the existing
`WaveformDataSource` interface — `RemoteWaveformDataSource`. The local
implementations stay as the fallback path for offline use. The side effect the
whole thing was done for: the waveform looks the same on every platform, and the
desktop no longer needs `flutter_soloud`.

### 5.3 The file: download once, play locally

```http
GET /v1/audio/{id}/file
Authorization: Bearer <access>
→ 200, Accept-Ranges: bytes, ETag: "<sha256>", Cache-Control: private, immutable
```

**There is no need to play over the network directly.** In shadowing, fragments
are looped every 2–3 seconds, and a `ClippingAudioSource` on top of a network
source would stutter on every repeat. The right path: on the first opening of a
lesson the file is downloaded once into the app cache (where the audio already
lives), and the player works with `AudioSource.file` as it does today.

- The link requires an `Authorization` header — it cannot be handed straight to
  the player or to an `Image.network`-like widget; download it through
  `dio.download`.
- `Range` is supported: a dropped download is resumed with a
  `Range: bytes=<already downloaded>-` header, answered by a `206` with a
  `Content-Range`.
- Check integrity by the `sha256` from the `POST /v1/audio` response or from
  `lesson.audio.sha256`: on a mismatch, delete the file and download it again.
- The name in the cache is the `audio_id` (plus the extension from
  `content_type`). The file is immutable: the content under one `audio_id` never
  changes, so no invalidation is needed.
- The cache is cleaned by LRU and on lesson deletion; **careful: one `audio_id`
  may belong to several lessons** (deduplication by `sha256`), so delete a file
  only when no live lesson references it.

## 6. Lessons

```json
{
  "id": "9f1c…",
  "title": "TED: How to learn",
  "duration_ms": 183400,
  "created_at": "2026-07-28T10:00:00.000Z",
  "updated_at": "2026-07-28T10:12:03.000Z",
  "deleted_at": null,
  "version": 3,
  "accent": "US",
  "level": "b1",
  "is_public": true,
  "topic": { "id": "4450…", "name": "Education" },
  "audio": { "id": "b21e…", "url": "…/v1/audio/b21e…/file", "content_type": "audio/mpeg",
             "size_bytes": 2938471, "sha256": "3f2a…", "duration_ms": 183400 },
  "segments": [
    { "index": 0, "text": "Hello there.", "start_ms": 0, "end_ms": 2100 },
    { "index": 1, "text": "How are you?", "start_ms": 2100, "end_ms": 4300 }
  ]
}
```

| Method | Path | Role | Meaning |
| --- | --- | --- | --- |
| GET | `/v1/lessons?since=&limit=&cursor=` | any | the public ones plus your own private ones, `updated_at desc` |
| GET | `/v1/lessons/{id}` | any | one lesson (your private one or a public one), `ETag: "<version>"` |
| PUT | `/v1/lessons/{id}` | author | create (`201`) or update (`200`) |
| DELETE | `/v1/lessons/{id}` | author | a soft delete, `204` |

The public catalog is shared: admin and owner edit and delete any public lesson.
A private lesson is edited and deleted by its author only (`user-pro` their own,
owner any). For anyone without creation or editing rights, `PUT`/`DELETE` gives
a `403 forbidden`; such buttons need not be shown.

The `is_public` field in the lesson body is the visibility. In a `PUT` only the
owner's value is honored (the default is `true`): for a `user-pro` the lesson is
always private and for an `admin` always public, whatever value was sent. On an
edit only the owner changes the visibility; for everyone else it is preserved.
Someone else's private lesson is indistinguishable from a missing one — a `404`
both in the list and by id.

### Creating a lesson

```http
PUT /v1/lessons/<a uuid generated by the client>
Content-Type: application/json

{ "title": "TED: How to learn",
  "audio_id": "b21e…",
  "created_at": "2026-07-28T10:00:00.000Z",
  "accent": "US",
  "level": "b1",
  "topic_id": "4450…",
  "segments": [ { "index": 0, "text": "…", "start_ms": 0, "end_ms": 2100 }, … ] }
```

It is a `PUT` and not a `POST` because the client generates the UUID: a repeat
after a lost connection creates no duplicate. `duration_ms` need not be sent —
the server takes the duration of the audio; send it and it will be a `422` if it
does not match.

### Categories: accent, level, topic

Three fields that are filled in on the lesson creation screen and that the
catalog is later filtered by (§6.1).

| Field | Values | On the creation screen |
| --- | --- | --- |
| `accent` | `US`, `UK` | a required choice, the values are hardcoded in the client |
| `level` | `a1`, `a2`, `b1`, `b2`, `c1`, `c2` | a required choice, the values are hardcoded in the client |
| `topic_id` | an id from `GET /v1/topics` | optional; without a choice the server assigns "Other" |

- `accent` and `level` are closed lists: the server changes them only with a
  release, so they can be kept as an `enum` in the client without going over the
  network for them. An empty or unknown value gives a `422` with the text of
  what was expected;
- **topics are a directory from the server**, edited by the owner, so the list
  must be requested (`GET /v1/topics`) rather than hardcoded. It may be cached,
  but refresh it on entering the creation screen and the filters: a topic may
  have been renamed or deleted;
- in a lesson response the topic arrives as an object `{id, name}` — a second
  request for the name is not needed. The name may change, the id may not: in
  the cache and in the filters rely on `topic.id`;
- a deleted topic does not break lessons: they move to "Other", and the next
  `GET` returns them with the new topic already.

**The invariants the server checks** (the same as in the app domain — do not let
them drift apart):

- at least one segment, with `index` running `0..N-1` without gaps;
- the boundaries strictly increase and are back to back:
  `segments[i].start_ms == segments[i-1].end_ms`;
- `segments[0].start_ms == 0`, `segments[N-1].end_ms == duration_ms` of the
  audio;
- the `audio_id` is available to the editor: either they uploaded it or the file
  is already published in a live lesson (otherwise a `404`).

Check this on the client before sending: the user should get the error from the
marker editor, not from the network.

### Editing a lesson

The same `PUT`, with the segments arriving **in full** — they are an aggregate
(this is exactly how `LessonLocalDataSource.upsertLesson` and the
`UpdateLessonContent` use case work). On an update the header is mandatory:

```http
If-Match: "3"
```

Take the version from `lesson.version` (or from the `ETag` of the last `GET`).
Without the header, or with a stale version, it is a `409 version_conflict`, and
the current lesson lies in `error.current`:

```json
{ "error": { "code": "version_conflict", "message": "version conflict",
             "current": { "id": "9f1c…", "version": 4, "segments": [ … ] } } }
```

For a single-user app this is rare (two devices editing one lesson). It is
enough to write `current` into the cache, show "the lesson was changed on
another device" and offer to redo the edit on top of the fresh version.
Overwriting someone else's version silently is not allowed.

An update lifts the soft delete: a `PUT` on a deleted lesson restores it.

### Deletion

`DELETE` is soft: the lesson stays with a `deleted_at` and a raised `version`,
so that the deletion spreads across devices. Locally the record is removed at
once. A repeated `DELETE` of the same lesson gives a `204`, and one of a foreign
or non-existent lesson a `404`.

### 6.1 Catalog filters

```http
GET /v1/lessons?accent=UK&level=c1&topic_id=4450…&limit=50
```

All three parameters are optional and combine with AND. The values are the ones
from the lesson body; case does not matter, and garbage gives a `422` rather
than an empty list. Pagination works as usual: `next_cursor` already accounts
for the filters, but the cursor must be reset when the filters change.

**Do not pass filters when synchronizing the cache.** A `since` delta with a
filter is incomplete: a lesson whose topic or level changed drops out of the
selection and the client never learns that it changed. The right order is to
pull the delta into the cache without filters and to filter locally; server-side
filters are for where the catalog is large and loads page by page.

### 6.2 Folders

A folder is an author's collection of lessons that already exist (a series, a
course, "mine for later"). The scenario: a user uploaded several lessons and
decides to group some of them into a folder. Folders are created by the same
roles as lessons (`user-pro`, `admin`, `owner`) and follow the same access and
visibility rules as lessons (§6): a public one is curated by `admin` and `owner`
and seen by everyone, a private one is seen by its author only; `user-pro` gets
always-private, `admin` always-public, and the owner goes by `is_public`.

```json
{
  "id": "7a2c…",
  "title": "TED Talks",
  "is_public": true,
  "created_at": "2026-08-30T10:00:00.000Z",
  "updated_at": "2026-08-30T10:12:03.000Z",
  "deleted_at": null,
  "version": 2,
  "lesson_count": 2,
  "lessons": [ { … a lesson as in §6 … } ]
}
```

| Method | Path | Role | Meaning |
| --- | --- | --- | --- |
| GET | `/v1/folders?since=&limit=&cursor=` | any | the public ones plus your own private ones, `updated_at desc`; the list carries `lesson_count` only, without `lessons` |
| GET | `/v1/folders/{id}` | any | the folder with its lessons, `ETag: "<version>"` |
| PUT | `/v1/folders/{id}` | author | create (`201`) or update (`200`): `{title, created_at?, is_public?}` |
| DELETE | `/v1/folders/{id}` | author | a soft delete, `204` |
| POST | `/v1/folders/{id}/lessons` | author | `{lesson_ids: […]}` — add lessons → the updated folder |
| DELETE | `/v1/folders/{id}/lessons/{lesson_id}` | author | remove a lesson from the folder, `204` |

- **the folder UUID is generated by the client** and creation goes through
  `PUT /v1/folders/{id}` (idempotent, as with lessons); `POST /v1/folders` is
  not supported;
- the list of lessons (`lessons`) arrives only where we asked for it (the
  details, creation/editing, changing the contents). The list
  (`GET /v1/folders`) carries only `lesson_count`, and the lessons themselves
  are pulled with `GET /v1/folders/{id}` on opening;
- **editing the metadata (title, visibility) requires `If-Match: "<version>"`** —
  as with lessons, a stale version gives a `409` with `error.current`. Adding
  and removing lessons, on the other hand, needs no `If-Match` (the operation is
  additive and idempotent) but does raise the folder `version` — so that the
  contents spread by delta;
- **only lessons available to the editor go into a folder** (public ones or
  their own private ones): an unavailable one gives a `404`. Adding the same
  lesson twice is not an error;
- a folder shows only the lessons **visible to the viewer**, in the order they
  were added: put a private lesson into a public folder and another user will
  not see it there, while `lesson_count` reflects the number visible to the
  viewer;
- deleting a lesson (`DELETE /v1/lessons/{id}`) removes it from every folder by
  itself; deleting a folder does not touch the lessons — it merely removes the
  grouping;
- synchronize folders like lessons (§7): a `since` delta without filters, and
  records with a `deleted_at` leave the cache.

### 6.3 The library feed: the root in one request

The home screen is the root: the folders and the lessons that lie in no folder.
Assembling it on the client from `/v1/lessons` and `/v1/folders` is **not
needed**: the two lists arrive out of step, and lessons from folders flash in
the list and disappear. The root is served ready-made.

```http
GET /v1/library?limit=50
```

```json
{
  "items": [
    { "type": "folder", "id": "7a2c…", "title": "TED Talks", "lesson_count": 2, … },
    { "type": "lesson", "id": "9f1c…", "title": "A standalone lesson", … }
  ],
  "next_cursor": null
}
```

- `type` is `"folder"` or `"lesson"`. The folder body is the same as in
  `GET /v1/folders` (with `lesson_count`, without `lessons`), and the lesson
  body the same as in `GET /v1/lessons`;
- once a folder is opened, its lessons are pulled with `GET /v1/folders/{id}`
  (§6.2);
- the sort is `updated_at desc` and the cursor is shared by both halves: `limit`
  and `cursor`/`next_cursor` work as everywhere (§7);
- a lesson is hidden from the root only when it lies in a folder **visible to
  the viewer**: someone else's private folder does not hide it, and neither does
  a softly deleted one;
- **with a filter** (`accent`/`level`/`topic_id`) the feed becomes a flat search
  over lessons: folders do not arrive (they have neither an accent nor a level),
  while lessons inside folders do, otherwise the filter would not find them;
- **`since` is not supported** — a `422`. This is a screen, not a source of
  synchronization: the contents of a folder live apart from the lesson and do
  not raise the lesson `version`, so "a lesson was put into a folder" cannot be
  expressed as a delta over lessons. The cache is filled by
  `GET /v1/lessons?since=` and `GET /v1/folders?since=` (§7), while the root is
  drawn from `/v1/library` — the network first, the cache as the fallback.

## 7. Synchronization and the cache

The scheme is deliberately simple, and it is worth keeping it simple so as not
to slide into offline-first ahead of time:

- **the server is the source of truth** and sqflite becomes a read cache; the
  catalog is shared, so the cache fills the same way for every role — other
  people's lessons in it are normal, and a `user` only reads;
- on start and on pull-to-refresh:
  `GET /v1/lessons?since=<the last known updated_at>` → apply the delta, and
  remove records with a non-empty `deleted_at` from the cache together with the
  orphaned audio;
- **without `since`** the list returns live lessons only; **with `since`** it
  returns the delta, including the deleted ones. That is the only difference and
  it matters: make the first run without `since`;
- save the new watermark as the maximum `updated_at` among the records received,
  not as the current device time (the clock may lie);
- writing (create, edit, delete) is available to `admin` and `owner` only, goes
  to the server and, on success, into the cache; with no connection there is an
  honest error in the UI, as there is today on a database failure;
- audio is cached by `audio_id`, and cleaning goes by LRU and by deleted
  lessons.

Pagination: `limit` (50 by default, 200 at most) and `cursor` from the
`next_cursor` of the previous response. A `next_cursor: null` means there are no
more pages. The cursor is a base64 string and must be url-encoded when
substituted into a query (`Uri.encodeQueryComponent`).

```json
{ "items": [ { … a lesson … } ], "next_cursor": "MjAyNi0wNy0yOFQxMDoxMjowMy4wMDBafDlmMWM…" }
```

A full offline queue (`pending_operations`, conflict resolution, deferred
uploads) is a separate stage, and it is only needed if editing lessons without a
connection is genuinely required. The seams for it are already there:
`version`/`If-Match` and the soft delete.

## 8. The owner tab: users and topics

A separate tab in the bottom navigation, visible only when `role == 'owner'`.
Today it has two sections — users (roles and deletion) and the topic directory;
statistics will be added here later, so the screen is worth building with room
for several blocks.

### 8.1 Users

| Method | Path | Request → response |
| --- | --- | --- |
| GET | `/v1/admin/users?q=&limit=&offset=` | → `{users: [{id, email, role, created_at}], total, limit, offset}` |
| PATCH | `/v1/admin/users/{id}/role` | `{ "role": "user" \| "user-pro" \| "admin" \| "owner" }` → the updated user |
| DELETE | `/v1/admin/users/{id}` | → `204` |

- `q` is a substring of the email, case-insensitive; `limit` goes up to 200, and
  `offset` walks the pages.
- The role in an access token lives up to 15 minutes, but the server verifies it
  against the database: a freshly promoted admin gets access immediately,
  without waiting for a new token.
- The owner set in the server configuration cannot be demoted or deleted — a
  `422`. The "make user" and "delete" buttons are better not shown for them at
  all; deleting yourself is not allowed either.
- **Deletion is irreversible and takes the user's sessions with it** — ask for
  confirmation with the email typed in or with an explicit "Delete forever"
  button. The public catalog does not suffer: the public lessons and folders of
  the deleted user pass to the owner. Their private lessons, folders and audio,
  though, are deleted with them — that is personal rather than shared, and it
  does not pass into anyone else's hands.
- Your own role in `/v1/me` may change at any moment: re-read it on entering the
  tab and hide the section on a `403`.

### 8.2 Topics

The directory of lesson topics. Anyone may read it (it is needed in the filters
and on the creation screen), and only the owner may edit it.

| Method | Path | Request → response |
| --- | --- | --- |
| GET | `/v1/topics` | → `{topics: [{id, name, is_default, created_at}]}` |
| POST | `/v1/topics` | `{name}` → `201`, the created topic |
| PATCH | `/v1/topics/{id}` | `{name}` → `200`, the updated topic |
| DELETE | `/v1/topics/{id}` | → `204` |

- the list arrives sorted: ordinary topics alphabetically and the `is_default`
  one ("Other") last. The same order suits the dropdown;
- the name is up to 60 characters and unique case-insensitively; an empty name
  or a duplicate gives a `422` with text ready to display;
- **deleting a topic is safe**: its lessons move to "Other" rather than
  vanishing. It is still worth warning about it in the dialog — the admin should
  understand that the markup of a part of the catalog will change. Re-read the
  lesson list after a deletion;
- do not show the "Delete" button for a topic with `is_default: true` — the
  server answers `422`. It can be renamed;
- refresh the topic cache after any edit: it is used in the catalog filters.

## 9. Handling errors in the UI

One place parses them, in `ApiClient`: the error body →
`ApiException(code, message, status, details)`. From there on the layers pass an
`ApiException`, not a `DioException`.

- network failures (`DioExceptionType.connectionError/timeouts`) — "no
  connection to the server" plus a retry button; that is not the same as an API
  error;
- `unauthorized` is handled by the interceptor and surfaces only when the
  refresh failed — then it is a sign-out to `/login`;
- a `not_found` while opening a lesson — remove it from the cache and show "the
  lesson was deleted";
- `version_conflict` — the scenario in §6, not a generic toast;
- `payload_too_large` / `unsupported_media_type` — check before sending, but
  still show the message from the server (it carries the reason);
- `rate_limited` — lock the sign-in form for a minute.

## 11. Order of work

Every stage leaves the app in a working state.

1. **The network and the tokens.** `ApiClient`, `TokenStorage`, the
   interceptors, `ApiException`. Verified against `/healthz` and `/v1/me`.
2. **Authorization.** The `auth` feature, the sign-in and registration screens,
   the router `redirect`, and an automatic sign-in by refresh on start. Lessons
   are still local at this step.
3. **Role-driven navigation.** The bottom tabs "Lessons", "Saved" and "Settings"
   for everyone plus "Users" for the owner (§4). "Saved" and "Settings" are
   placeholders; a `user` has no creation, editing or deletion on "Lessons".
4. **Audio.** `POST /v1/audio` on the creation screen (with progress and
   cancellation), `RemoteWaveformDataSource`, and the file cache by `audio_id`.
   This is also where waveform behavior is aligned across platforms and the
   local duration measurement is removed.
5. **Lessons.** `LessonRemoteDataSource`, assembling the "server plus cache"
   repository, downloading audio when a lesson is opened, `If-Match` on edits.
   Here too: choosing the accent, the level and the topic on the creation screen
   (§6, "Categories").
6. **Delta synchronization** by `since`, cache cleanup, pull-to-refresh.
7. **Catalog filters** by accent, level and topic (§6.1).
8. **The "Management" tab** for the `owner`: users and the topic directory (§8).
9. **Later, if needed:** the contents of "Saved" and "Settings", statistics in
   the owner tab, an offline write queue, sign-in through Apple/Google
   (mandatory for iOS if social sign-in appears).

## 12. Profile, progress and settings

### 12.1 The profile (study data)

The `name`, `studied_language` and `daily_goal_minutes` fields arrive in the
`user` object (the auth responses and `GET /v1/me`). They are set at
registration and edited in "Settings":

```http
PATCH /v1/me            { "name": "Anna", "studied_language": "en", "daily_goal_minutes": 30 }
→ 200  { …, "name": "Anna", "studied_language": "en", "daily_goal_minutes": 30 }
```

- the fields that are sent change, the omitted ones do not; an empty string
  clears a field;
- the name is up to 100 characters; `studied_language` is a short code (the
  server lowercases it, up to 16 characters); `daily_goal_minutes` is 0..1440,
  otherwise a `422`;
- show the studied language and the daily goal in "Settings" and on the progress
  screen.

### 12.2 Progress

Every authorized user has progress. The client batches the activity and sends it
as events; whether a lesson is complete is decided by the **client** (the
segment repeat threshold is only a hint from the server, see §12.3).

| Method | Path | Body / response |
| --- | --- | --- |
| POST | `/v1/progress/events` | `{listened_ms?, segment_repeats?, lesson_id?, completed?}` → the fresh summary |
| GET | `/v1/progress` | the summary |
| GET | `/v1/progress/history?days=30` | `{days: [{day, listened_ms, segment_repeats}]}` over a window (1..365) |

```json
{ "today": { "day": "2026-08-06", "listened_ms": 180000, "segment_repeats": 10 },
  "totals": { "listened_ms": 180000, "segment_repeats": 10, "lessons_completed": 1 },
  "week_minutes": 3,
  "week": [ { "day": "2026-08-06", "listened_ms": 180000, "segment_repeats": 10 } ],
  "recent_lesson_ids": ["9f1c…"],
  "daily_goal_minutes": 20,
  "completion_reps": 10 }
```

- send an event periodically: `listened_ms` is what was listened to since the
  last report and `segment_repeats` is how many segment repeats were made; the
  server accumulates them per day (UTC);
- a `lesson_id` in an event adds the lesson to the "last 5"
  (`recent_lesson_ids`); only a visible lesson counts (a public one or your own
  private one), otherwise a `404`;
- once the client decides by its own counter that every segment was repeated the
  required number of times (`completion_reps`), send `completed: true` with the
  `lesson_id`. The mark is set once — sending it again does not double the
  completed counter;
- `week` holds the last 7 days for the trend chart and `week_minutes` is the sum
  of minutes over them; take the full history for longer charts from `history`;
- `daily_goal_minutes` in the summary duplicates the profile — handy for drawing
  "X of the goal today" without a second request.

### 12.3 Settings (the completion threshold)

| Method | Path | Role | Body / response |
| --- | --- | --- | --- |
| GET | `/v1/settings` | any | `{ "lesson_completion_reps": 10 }` |
| PATCH | `/v1/settings` | owner | `{ "lesson_completion_reps": 15 }` (1..1000) → the current settings |

`lesson_completion_reps` is how many times each segment must be repeated for a
lesson to count as complete. The value is curated by the owner (the "Management"
tab) and read by everyone: the client takes it as the target for the lesson
progress bar and decides for itself when to send `completed`. It also arrives in
the progress summary as `completion_reps`.
